# /readable

전문 지식·코드 관련 설명을 **중간 레벨 개발자가 한 번에 읽고 이해할 수 있는 형태**로 바꿔서 답한다.

## Usage

```
/readable <question>          # 질문을 가독성 우선으로 설명
/readable <question> --deep   # 처음부터 여러 청크로 나눠 깊게 설명
/readable --more              # 직전 설명의 다음 청크 이어서 설명
```

`<question>` 이 코드베이스에 관한 것이면 먼저 실제 파일을 읽어 사실을 확인한 뒤 설명한다. 추측으로 채우지 않는다.

## 독자 정의 (모든 판단의 기준)

- IT 회사 재직자, **주니어와 시니어 사이**. 코드는 읽지만 용어 지식은 생각보다 얕다.
- 알고 있다고 가정해도 되는 것: 변수, 함수, 클래스, API, 데이터베이스, Git, 배포 같은 일상 용어.
- 설명을 붙여야 하는 것: 아키텍처 패턴 이름, 알고리즘 이름, 프로토콜 세부, 프레임워크 내부 개념,
  영어 약어(예: CQRS, IdP, mTLS, WAL, backpressure), 그 회사/그 레포에서만 쓰는 이름.

## 작성 규칙

### 1. 단어
- 어려운 단어보다 **평소에 쓰는 단어**를 쓴다. (예: "영속화한다" → "저장한다", "오케스트레이션" → "순서대로 실행한다")
- 전문 용어를 꼭 써야 하면 **처음 나올 때 한 줄 설명을 괄호로** 붙인다.
  `멱등성(같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질)`
- 코드에 실제로 존재하는 타입·함수·파일 이름은 **비유로 바꾸지 말고 그대로** 쓴다.
  ("봉투" 같은 임의 비유 금지 → `SystemNotification`)

### 2. 순서 (서순)
아래 순서를 기본으로 하고, 질문 성격에 맞게 필요한 단계만 남긴다.

| 단계 | 내용 | 목적 |
|---|---|---|
| 1 | 한 줄 결론 | 바쁜 사람이 여기서 멈춰도 답이 됨 |
| 2 | 맥락 — 왜 이게 필요한지, 어디에 쓰이는지 | 이해의 발판 |
| 3 | 동작을 순서대로 (1→2→3) | 단계적 이해 |
| 4 | 값·비교·항목이 많으면 표/리스트/JSON | 시각적 정리 |
| 5 | 실제 위치 (`file.ts:42`) 또는 근거 | 검증 가능성 |
| 6 | 주의점 / 흔한 오해 (있을 때만) | 실수 예방 |

앞 단계를 읽지 않으면 뒤 단계가 이해되지 않게 쓴다. 즉 **맥락 없이 결론만, 결론 없이 세부만** 쓰지 않는다.

### 3. 출력 형식
- 항목이 3개 이상 나열되면 → **리스트**
- 항목마다 속성이 2개 이상 비교되면 → **표**
- 실제 데이터 구조·응답 형태·설정값을 보여줄 때 → **JSON 코드블록** (필드마다 주석 대신 표로 설명 병기)
- 흐름·단계가 있으면 → **번호 목록**
- 문단만 길게 이어 쓰지 않는다. 한 문단은 3줄 이내.

### 4. 길이와 분할
- **한 청크는 한글 500~600자 이내**(코드블록·표 제외)로 맞춘다.
- 내용이 그보다 길어지면 자르고, 마지막에 다음 형식으로 명시한다:

  > 여기까지가 1/3입니다. 다음은 **<다음 청크 제목>** 입니다. 계속 볼까요? (`/readable --more`)

- 사용자가 확인하기 전에 다음 청크를 이어서 쓰지 않는다.
- 남은 청크의 제목 목록을 미리 한 줄로 보여주어 전체 그림을 알 수 있게 한다.

### 5. 마지막 자기 점검 (답변 직전 필수)
답변을 내보내기 전에 아래를 확인하고, 걸리는 항목이 있으면 고친 뒤 출력한다.

- [ ] 사실 확인: 파일·함수·설정값을 실제로 읽고 썼는가? 읽지 않고 **추측한 부분이 있는가?**
- [ ] 추측이 남아 있으면 지우거나 `※ 확인 필요:` 로 표시했는가?
- [ ] 설명 없이 지나간 전문 용어가 있는가?
- [ ] 1단계만 읽어도 질문에 답이 되는가?
- [ ] 500~600자를 넘겼는데 분할 안내 없이 끝냈는가?
- [ ] 원래 질문에서 답하지 않고 넘어간 부분이 있는가?

## 답변 템플릿

```
**한 줄 결론**
<질문에 대한 직접적인 답 한 문장>

**왜 필요한가 / 어디서 쓰이나**
<맥락 2~3줄>

**어떻게 동작하나**
1. <단계>
2. <단계>
3. <단계>

**정리**
| 항목 | 값 | 설명 |
|---|---|---|

**확인할 위치**
- `path/to/file.ts:42` — <무엇이 있는지>

**주의점**
- <흔한 오해나 함정>
```

필요 없는 섹션은 지운다. 템플릿을 채우기 위해 빈 내용을 만들지 않는다.

## 하지 않을 것

- 설계 원칙 강의, 변경 이력 해설, 마무리 요약 문단 추가
- 사용자가 묻지 않은 범위로 설명 확장
- 코드베이스를 읽지 않은 상태에서 "아마 ~일 것입니다" 로 답하기
